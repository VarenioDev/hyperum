## ADR-001. FastAPI для backend

**Дата:** сентябрь 2026

### Контекст

Нужен был Python-фреймворк для REST API, обслуживающий PWA и внешние интеграции. Стек — Python (ML-часть).

### Решение

FastAPI.

### Обоснование

- **Async из коробки** — важен для одновременных запросов от 30+ учеников.
- **Pydantic-валидация** — типизация запросов/ответов, автоматическая документация.
- **OpenAPI/Swagger** — автоматически генерируется, удобно для научрука и комиссии.
- **Скорость разработки** — один разработчик, нужен быстрый результат.
- **Активное сообщество** — много примеров, легко искать решения.

### Альтернативы

| Вариант | Почему отклонён |
|---------|-----------------|
| Django + DRF | Тяжёлый, много «магии», async не везде |
| Flask | Минималистичен, но нет встроенной валидации и OpenAPI |
| Litestar | Хорош, но меньше комьюнити |
| aiohttp | Слишком низкоуровневый |

### Последствия

**Плюсы:**
- Быстрая разработка.
- Понятная структура: роутер → сервис → БД.
- Автодокументация.

**Минусы:**
- Нет встроенной админки (как в Django).
- Нет ORM-миграций (пишем SQL-миграции руками).

## ADR-002. PostgreSQL + Neo4j (две БД)

**Дата:** сентябрь 2026

### Контекст

Нужно хранить:
1. Транзакционные данные: пользователи, ответы, mastery, назначения.
2. Граф знаний: навыки, prerequisit'ы, связи между ними.

### Решение

Две БД:
- **PostgreSQL 16** — транзакции, RLS, аналитика.
- **Neo4j 5** — граф знаний, prerequisite-обход.

### Обоснование

**Почему PostgreSQL:**
- Надёжность, зрелость.
- RLS (Row-Level Security) — критично для multi-tenancy.
- JSONB для опций задания.
- Отличная работа с агрегациями (mastery по классу, статистика).

**Почему Neo4j:**
- Граф — естественная модель для prerequisite.
- Cypher — читаемые запросы обхода.
- Быстрый поиск «всех предков навыка».
- Визуализация через Neo4j Browser для отладки.

**Почему две, а не одна:**
- В PostgreSQL граф-обход через recursive CTE — работает, но медленнее и менее удобно.
- В Neo4j транзакционные запросы (INSERT, UPDATE) — работают, но RLS, индексы, JSONB уступают PostgreSQL.
- Разделение ролей: PostgreSQL = истина для оценок, Neo4j = истина для структуры.

### Альтернативы

| Вариант | Почему отклонён |
|---------|-----------------|
| Только PostgreSQL | Recursive CTE медленнее, неудобно для графа |
| Только Neo4j | Нет RLS, слабая аналитика, JSONB хуже |
| PostgreSQL + граф в JSONB | Теряются преимущества графовой БД |
| ArangoDB (multi-model) | Менее зрелый, меньше комьюнити |

### Последствия

**Плюсы:**
- Каждая БД на своей сильной стороне.
- Graph traversal через Cypher — быстро.
- Аналитика через SQL — мощно.

**Минусы:**
- **Двойная синхронизация** — mastery нужно держать в обеих.
- Два контейнера в Docker — больше памяти.
- Возможна рассинхронизация (решается best-effort sync).

**Техдолг:** `sync_mastery_to_neo4j` хардкодит `tenant_id='school_lyceum'`. Для demo работает некорректно.

## ADR-003. RLS для multi-tenancy

**Дата:** сентябрь 2026

### Контекст

Нужна изоляция данных между tenant'ами: `school_lyceum`, `demo`, в будущем — `platform_polyum`.

Три подхода:
1. Отдельная БД на tenant.
2. Отдельная схема на tenant.
3. Общая схема + RLS.

### Решение

Общая схема + RLS (Row-Level Security).

### Обоснование

- **Один разработчик, один сервер** — не хотим плодить БД и схемы.
- **Cross-tenant данные** — банк заданий и таксономия общие. Отдельные БД усложнили бы JOIN'ы.
- **RLS** — декларативен: политика в SQL, а не в коде. Невозможно «забыть» WHERE.
- **`FORCE ROW LEVEL SECURITY`** — политика действует даже на владельца таблицы.

### Как реализовано

```sql
ALTER TABLE responses ENABLE ROW LEVEL SECURITY;
ALTER TABLE responses FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation_responses ON responses
  USING (tenant_id = current_setting('app.current_tenant', true));
```

Backend при каждой сессии:
```python
session.execute(text("SELECT set_config('app.current_tenant', :t, true)"), {"t": tenant_id})
```

`SET LOCAL` — в рамках транзакции, сбрасывается при возврате в пул.

### Альтернативы

| Вариант | Почему отклонён |
|---------|-----------------|
| Отдельная БД на tenant | Cross-tenant JOIN'ы невозможны |
| Отдельная схема | Сложнее миграции, нет RLS |
| Фильтрация в коде | Легко забыть WHERE, уязвимость |
| Отдельные пользователи БД | Не работает для динамических tenant'ов |

### Последствия

**Плюсы:**
- Изоляция на уровне БД, не кода.
- Один набор миграций.
- Один сервер.

**Минусы:**
- **Ошибка в `tenant_session` = утечка данных**. Решается `FORCE RLS`.
- Сложнее отлаживать (нужно «включить» RLS).
- Плохо масштабируется на 100+ tenant'ов (не наш случай).

## ADR-004. PWA вместо нативных приложений

**Дата:** сентябрь–октябрь 2026

### Контекст

Ученикам нужен мобильный интерфейс для решения тестов.

### Решение

PWA (Progressive Web App): React + Vite + Tailwind + vite-plugin-pwa.

### Обоснование

- **Одна кодовая база** — iOS, Android, desktop.
- **Установка на домашний экран** — без App Store / Google Play.
- **Обновления мгновенные** — никаких ревью.
- **Офлайн** (в планах) — service worker.
- **Один разработчик** — не потянуть 2 нативных приложения.

### Альтернативы

| Вариант | Почему отклонён |
|---------|-----------------|
| React Native | Отдельная сборка для iOS/Android, нужен Mac |
| Flutter | Учить Dart, нет переиспользования с backend |
| Мобильный веб без PWA | Не устанавливается, нет офлайна |
| Нативные iOS + Android | Двойная работа, не для одного разработчика |

### Последствия

**Плюсы:**
- Один проект — все платформы.
- Быстрые итерации.
- Manifest + Service Worker → standalone-режим.

**Минусы:**
- Нет push-уведомлений в iOS Safari (до недавнего времени).
- Ограниченный доступ к железу.
- Install-баннер на iOS только через «Поделиться → На экран».

Изначально дашборд учителя был на Streamlit. Работал, но:
- Не вписывался в дизайн PWA (другая визуальная стилистика).
- Отдельный порт, отдельный процесс, отдельная авторизация.

Перенести дашборд учителя в PWA: `/teacher`, `/teacher/class/:id`, `/teacher/class/:id/generate`.

- **Единый дизайн** — стеклянные карточки, brand-цвета, Montserrat.
- **Единая авторизация** — те же cookies, тот же API.
- **Мобильный-first** — учитель может работать с телефона.
- **Переиспользование компонентов** — `Header`, `SkillCard`, `GraphView`.

### Альтернативы

| Вариант | Почему отклонён |
|---------|-----------------|
| Оставить Streamlit | Разъезжается дизайн и авторизация |
| Django admin | Не для учеников, не кастомизируется |
| Отдельное React-приложение | Дублирование сборки, дублирование API-клиента |

### Последствия

**Плюсы:**
- Единый продукт.
- Один деплой.
- Мобильный доступ.

**Минусы:**
- Дольше разработка (Streamlit — 3 дня, React — 3 недели).
- Учитель должен уметь пользоваться PWA (тривиально).

**Техдолг:** Streamlit-код не удалён. `dashboard/` и `requirements.txt` (со streamlit) остаются. В `requirements-backend.txt` их нет.

## ADR-006. DeepSeek для разметки заданий

**Дата:** октябрь 2026

### Контекст

Нужна LLM для автоматической разметки заданий: определение primary/secondary навыков, сложности, reasoning.

Первоначально использовался GigaChat (Сбер).

### Решение

DeepSeek `deepseek-chat`.

### Обоснование

- **Качество разметки** — субъективно выше, чем у GigaChat.
- **Дешевле** — ~в 5–10 раз.
- **Быстрее** — ответ за 5–15 сек на батч из 10 заданий.
- **JSON-mode** — `response_format: {type: "json_object"}` — стабильный JSON.
- **Не требует сертификата** — в отличие от GigaChat (там нужен сертификат НУЦ Минцифры).

### Альтернативы

| Вариант | Почему отклонён |
|---------|-----------------|
| GigaChat | Дороже, медленнее, менее стабильный JSON |
| OpenAI GPT-4 | Дорого, ограничения по РФ |
| Локальная Mistral (Ollama) | Требует GPU, качество ниже |
| YandexGPT | Нестабильный API в тот момент |

### Последствия

**Плюсы:**
- Дешёвая разметка.
- Быстрая.
- Хорошее качество.

**Минусы:**
- **Зависимость от внешнего сервиса** — если API недоступен, разметка стоит.
- **Данные уходят в Китай** — для заданий (не для PII) допустимо.
- **Батчинг обязателен** — одиночные запросы медленнее.

**GigaChat-скрипт оставлен** как референс и fallback.

## ADR-007. Multi-skill разметка (primary + secondary)

**Дата:** октябрь 2026

### Контекст

Изначально задание связывалось с **одним** навыком. Но реально большинство задач требует **комбинации** навыков: задача на вложенные циклы требует и `for`, и понимания вложенности.

### Решение

В `task_labels` добавить флаг `is_primary`:
- Ровно **один** primary-навык — что проверяется в первую очередь.
- **0–2** secondary-навыка — что задействовано попутно.
- PK расширен до `(task_id, skill_id, model)`.

### Обоснование

- **Реалистичнее** — задача редко проверяет ровно один навык.
- **Лучше подбор** — учитываем «широту» задания.
- **Лучше mastery** — secondary-навык тоже обновляется (с весом 0.7).

### Альтернативы

| Вариант | Почему отклонён |
|---------|-----------------|
| Один навык на задание | Не отражает реальность |
| 3+ навыков | Размывает сигнал, сложнее оценивать |
| Без primary | Непонятно, что «главное» |

### Последствия

**Плюсы:**
- Точнее mastery.
- Богаче scoring.

**Минусы:**
- **Сложнее разметка** — нужно объяснить LLM правила.
- **Сложнее запросы** — `HAVING MAX(CASE WHEN is_primary...)`.
- **Сложнее mastery** — нужны веса.

### Как это повлияло на mastery

Формула стала взвешенной:
```
w_attempts = Σ (1.0 if primary else 0.7)
w_correct  = Σ (weight × correct)
mastery = (w_correct + 0.5×3) / (w_attempts + 3)
```

## ADR-008. Взвешенный mastery + байесовское сглаживание

**Дата:** октябрь 2026

### Контекст

Изначально mastery = `correct / attempts`. Просто, но два дефекта:
1. **При 1 попытке** — либо 0, либо 1. Слишком категорично.
2. **Не учитывает primary/secondary** — все навыки весят одинаково.

### Решение

Взвешенный mastery + байесовское сглаживание:

```python
PRIOR = 0.5     # сглаживание к среднему
WEIGHT = 3.0    # виртуальных попыток prior'а

mastery = (w_correct + PRIOR * WEIGHT) / (w_attempts + WEIGHT)
```

### Обоснование

**Байесовское сглаживание:**
- При 1 попытке `correct / 1` = 0 или 1 — не доверяем.
- При 10+ попытках — доверяем статистике.
- `WEIGHT = 3` — компромисс: не слишком медленно «учится», не слишком доверчиво.

**Взвешивание:**
- Primary = 1.0 — задание проверяет навык по существу.
- Secondary = 0.7 — сопутствующий.

### Альтернативы

| Вариант | Почему отклонён |
|---------|-----------------|
| Наивный `correct/attempts` | Категоричен при малых данных |
| Laplace smoothing (`(c+1)/(a+2)`) | Слабее байесовского, prior = 0.5 неявно |
| Только взвешенный, без сглаживания | Дефект при 1 попытке |
| Только сглаживание, без весов | Не учитывает multi-skill |

### Последствия

**Плюсы:**
- Устойчивость при малых данных.
- Учёт multi-skill.
- Интерпретируемые числа.

**Минусы:**
- Не учитывает **порядок** ответов (это будет BKT).
- Не учитывает **забывание**.
- `PRIOR = 0.5` и `WEIGHT = 3` — эмпирические константы, нужно тюнить.

**Замечание:** в `student_mastery` пишутся **сырые** attempts/correct (не взвешенные) — для UI. Mastery считается на лету.

## ADR-009. IRT-подобный scoring заданий

**Дата:** сентябрь 2026

### Контекст

Нужна функция, оценивающая полезность задания для конкретного ученика.

### Решение

IRT-подобная функция полезности:

```python
p_correct = sigmoid(4 × (mastery − difficulty))
base = exp(−(p_correct − 0.7)² / 0.08)
if mastery < 0.5: base *= 1.4
score = base / (1 + 0.5 × usage_count)
```

### Обоснование

**Почему IRT-подобный:**
- IRT — стандарт в educational data mining.
- 1PL (Rasch) — простейшая модель: только сложность + способность.
- Позволяет вычислить вероятность правильного ответа.

**Почему пик при 0.7, а не 0.5:**
- Задачи с p = 0.5 — на грани возможностей, фрустрируют.
- p = 0.7 — «зона ближайшего развития» по Выготскому.
- Комфортно и продуктивно.

**Почему бонус слабым (×1.4):**
- Слабые ученики нуждаются в большем числе заданий.
- Не ×2, чтобы diversity не страдала.

**Почему diversity-штраф:**
- Распределение заданий по классу.
- Не давать всем одно и то же.

### Альтернативы

| Вариант | Почему отклонён |
|---------|-----------------|
| Random | Не персонализированно |
| «Все задания на слабые навыки» | Однообразие, фрустрация |
| 2PL IRT | Нужны данные для калибровки дискриминации |
| Contextual bandit | Нужны A/B-данные, ещё не собраны |

### Последствия

**Плюсы:**
- Персонализация.
- Diversity.
- Интерпретируемые параметры.

**Минусы:**
- **Эвристика** — не учится на данных. Это baseline для будущего BKT.
- Константы (4, 0.08, 1.4, 0.5) — эмпирические.
- Не учитывает порядок и историю (только текущий mastery).

**См. `research.md`** — этот scoring явно обозначен как baseline для гипотезы H2/H3.

## ADR-010. Prerequisite-фильтр через Neo4j

**Дата:** сентябрь 2026

### Контекст

Если ученик слабо знает `s_for`, нет смысла давать `s_nested`.

### Решение

При генерации теста запрашивать Neo4j:

```cypher
MATCH (st:Student {id: $stid})-[m:MASTERY]->(pre:Skill)
WHERE m.value < 0.5
MATCH (pre)-[:PREREQUISITE]->(target:Skill)
WHERE target.id IN $sids
RETURN DISTINCT target.id AS blocked
```

Заблокированные задания с primary-навыком = blocked отсеиваются.

### Обоснование

- Neo4j естественно хранит prerequisite.
- Порог 0.5 совпадает с цветовой границей «weak/learning».
- Best-effort: если Neo4j недоступен — фильтр не применяется (лучше дать что-то, чем ничего).

### Альтернативы

| Вариант | Почему отклонён |
|---------|-----------------|
| Только primary, без prerequisite | Фрустрация учеников |
| Порог 0.4 (мягче) | Слабее защита |
| Порог 0.6 (жёстче) | Слишком мало заданий |
| Кэш prerequisite в PostgreSQL | Дублирование, рассинхронизация |

### Последствия

**Плюсы:**
- Меньше фрустрации.
- Ученик «дорастает» до сложных заданий.

**Минусы:**
- **Fallback может пропустить** — если всё заблокировано, фильтр игнорируется.
- Проверяет только `primary_skill`, не `secondary`.

## ADR-011. Хранение mastery в PostgreSQL, копия в Neo4j

**Дата:** сентябрь 2026

### Контекст

Mastery нужен:
1. Для аналитики (`/mastery/class`, `/mastery/student`).
2. Для визуализации графа (`/graph/student`).
3. Для scoring при генерации.

### Решение

- **Источник истины** — PostgreSQL (`student_mastery`).
- **Копия для визуализации** — Neo4j (ребро `MASTERY`).
- Синхронизация — best-effort, при каждом ответе.

### Обоснование

**Почему PostgreSQL как источник:**
- RLS.
- Агрегации (AVG по классу).
- JOIN'ы (ученик × навык).
- Транзакции.

**Почему Neo4j как копия:**
- Визуализация графа — там уже узлы `:Skill`.
- Удобно достать «мастерство по всему графу» одним запросом.

**Почему не наоборот:**
- Neo4j хуже для агрегаций.
- Neo4j не поддерживает RLS.

### Альтернативы

| Вариант | Почему отклонён |
|---------|-----------------|
| Только PostgreSQL | При визуализации графа — N+1 запрос |
| Только Neo4j | Нет RLS, нет агрегаций |
| Кэш в Redis | Ещё один компонент, не оправдан |

### Последствия

**Плюсы:**
- Быстрая визуализация.
- Мощная аналитика.

**Минусы:**
- **Возможна рассинхронизация** — если Neo4j лежал при ответе.
- Решается периодическим `ml/sync_mastery_to_neo4j.py`.

## ADR-012. Отдельный tenant для demo

**Дата:** октябрь 2026

### Контекст

На лендинге — публичный demo-виджет: гость пишет «что знаю / что не знаю», получает тест и граф.

### Решение

Отдельный tenant `demo`:
- Своя группа `dddddddd-...`.
- Свои «гости» (роль `student`, tenant `demo`).
- Rate limit по IP (5/час).
- Cleanup гостей старше 24 ч.

### Обоснование

- **Изоляция** — гости не пересекаются с реальными учениками.
- **Безопасность** — нельзя случайно показать PII лицея.
- **Аналитика чистая** — статистика по школе не засоряется demo-ответами.
- **Cleanup** — можно удалять всё разом.

### Альтернативы

| Вариант | Почему отклонён |
|---------|-----------------|
| Demo в `school_lyceum` | Смешивание данных, PII-риск |
| Отдельная БД | Overhead, не нужен |
| Mock без БД | Не показывает реальную работу системы |

### Последствия

**Плюсы:**
- Изоляция.
- Витрина работает.
- Комиссия видит систему в действии.

**Минусы:**
- **Rate limit in-memory** — теряется при рестарте.
- **Cleanup нужен** — иначе таблицы растут.
- **Хардкод `tenant_id='school_lyceum'`** в sync — для demo некорректно, но не критично.

**Точка роста:** Redis для rate limit + cleanup по cron.

## ADR-013. Регистрация ученика по инвайт-коду

**Дата:** октябрь 2026

### Контекст

Как ученики попадают в систему?

### Решение

- Учитель создаёт класс → получает **6-символьный инвайт-код**.
- Ученик вводит код на `/join`.
- Создаётся `users` (status='pending') + `memberships` (status='pending').
- Учитель подтверждает → `active`.

### Обоснование

- **Просто для ученика** — не надо вводить email учителя, приглашение.
- **Контроль учителя** — approve/reject.
- **Работает и офлайн** — учитель пишет код на доске.
- **Без email-рассылки** — не нужен SMTP.

### Альтернативы

| Вариант | Почему отклонён |
|---------|-----------------|
| Только приглашение по email | Нужен SMTP, спам-фильтры |
| Открытая регистрация | Кто угодно попадёт в класс |
| SSO школы | Не везде есть |
| Ссылка с токеном | Длинная, неудобно диктовать |

### Последствия

**Плюсы:**
- Просто.
- Без внешних зависимостей.
- Контроль учителя.

**Минусы:**
- **Код можно передать другим** — но approve фильтрует.
- **При утечке кода** — regenerate.
- **Ученик ждёт approve** — не сразу может работать.

**Техдолг:** при логине нет проверки `status`. Ученик с `pending` может логиниться (но увидит пустой класс).

## ADR-014. `SET LOCAL` для RLS

**Дата:** сентябрь 2026

### Контекст

Как устанавливать `app.current_tenant` в PostgreSQL?

### Решение

```python
session.begin()
session.execute(text("SELECT set_config('app.current_tenant', :t, true)"), {"t": tenant_id})
```

Третий аргумент `true` = `is_local`. Работает в рамках транзакции.

### Обоснование

- **Безопасность** — при возврате соединения в пул переменная сбрасывается.
- **Иначе** — «протечка»: следующий запрос на том же соединении увидит чужой tenant.
- **`SET LOCAL`** — стандартный механизм PostgreSQL для этого.

### Альтернативы

| Вариант | Почему отклонён |
|---------|-----------------|
| `SET` (без LOCAL) | Протечка через пул |
| Отдельные connection pool на tenant | Не масштабируется |
| Передача tenant_id в каждый запрос | Легко забыть |

### Последствия

**Плюсы:**
- Безопасно.
- Просто.

**Минусы:**
- **Транзакция обязательна** — нельзя set_config вне неё.
- `expire_on_commit=False` — иначе атрибуты становятся stale.

## ADR-015. JWT в cookies + Bearer

**Дата:** октябрь 2026

### Контекст

Как передавать JWT от клиента к серверу?

### Решение

**Два способа одновременно:**

1. **httpOnly cookies** — для PWA (`hyperum_access`, `hyperum_refresh`).
2. **Bearer-токен в JSON** — для API-интеграций (ПолиУм).

### Обоснование

- **Cookies — безопаснее для браузера:** httpOnly → XSS не украдёт токен.
- **`samesite=lax`** → защита от CSRF.
- **Bearer — стандарт для машин:** интеграции получают токен из JSON.
- **Оба одновременно** — PWA работает с cookies, внешние клиенты — с Bearer.

### Альтернативы

| Вариант | Почему отклонён |
|---------|-----------------|
| Только localStorage | XSS-уязвимость |
| Только cookies | Неудобно для API-клиентов |
| Только Bearer | XSS-уязвимость в PWA |

### Последствия

**Плюсы:**
- Гибкость.
- Безопасность для PWA.

**Минусы:**
- **`secure=False` сейчас** — техдолг (в проде нужно True).
- **Нет `refresh`-эндпоинта** — access-токен живёт 1 час, потом перелогин.

**Техдолг:** реализовать `POST /auth/refresh` (FR-8.3).

## ADR-016. Отказ от Contextual Bandit в MVP

**Дата:** октябрь 2026

### Контекст

Изначально предполагалось, что выбор задания — задача contextual bandit (обучение с подкреплением).

### Решение

**Отложить до post-MVP.** Сейчас — IRT-подобный scoring (эвристика).

### Обоснование

- **Нужны данные** — bandit обучается на исходах (reward).
- **Нужна рандомизация** — random exploration для обучения.
- **Нужны A/B-метрики** — без них не оценить.
- **Данных пока мало** — 67 учеников × 6 месяцев = порядка 3000–5000 ответов.

**Научный план:** сначала BKT (Level 1) → graph-BKT (Level 2) → bandit (Level 3, если время).

### Альтернативы

| Вариант | Почему отклонён |
|---------|-----------------|
| Bandit сразу | Нет данных, нет A/B-инфраструктуры |
| Offline-обучение на исторических данных | Смещение (мы видим только то, что дали) |
| Симуляция | Не отражает реальных учеников |

### Последствия

**Плюсы:**
- Реалистичный план.
- Baseline (H1) работает сейчас.

**Минусы:**
- Не «настоящий ML» пока.
- Требуется время на сбор данных.

**См. `research.md`** — план фаз 0–4.
