# Генерация тестов: F68, F69, F28, F76

Реализовано локально 2026-10-15. Развёртывание выполняет владелец проекта.

## Поведение

- Выбираются подтверждённые ученики своего класса. По умолчанию выбраны все доступные; поиск по имени не сбрасывает скрытые отметки.
- Персональный подбор включён по умолчанию. «Не персонализировать» создаёт один набор в одинаковом порядке для всех выбранных учеников.
- Для общего теста усредняется освоение каждого навыка только по выбранным ученикам. Отсутствующая история учитывается как 0.5; затем применяется существующий алгоритм подбора.
- В превью доступны полный Markdown/LaTeX-текст, варианты ответа, раскрываемый ответ, основной навык и сложность. Вложения — отдельные F62/F64.
- Замена сначала сохраняет навык. Если альтернатив нет, ищет соседние навыки по связям PREREQUISITE в пределах темы: ближайшие по графу, затем близкие по сложности, затем по скорингу. При недоступном графе возможна только замена внутри исходного навыка.
- В общем режиме позиция заменяется у всех получателей. В персональном — у одного. Исключаются текущие и ранее отклонённые задания этого набора; для нового подбора история исключений очищается.
- Изменение настроек сбрасывает несохранённое превью. После сохранения настройки и замены заблокированы: можно отправить черновик или начать новый тест.
- Сервер проверяет владение классом, состав получателей и допустимость заданий. При сохранении общего теста проверяется совпадение порядка. При отправке повторно проверяется доступ получателей.

Миграций, переразметки и изменений заданий не требуется. Общий тест хранится существующими строками `assignment_tasks` на каждого ученика; прогресс остаётся индивидуальным. Режим подбора нужен для превью и проверки сохранения, отдельный столбец в БД не добавляется.

## Локальные проверки

Из корня проекта в PowerShell:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -p test_assignment_generation.py -v
cd pwa
npm run test:generation
npm run build
```

Тесты используют искусственные задания и подменяют хранилища. Рабочая база и VPS не нужны. API-тестам нужен `httpx` (есть в текущем локальном окружении); серверу в продакшене он для этой функции не требуется.

## Самостоятельное развёртывание

Сначала включить перечисленные исходники и тесты в свой коммит и отправить его в репозиторий. Здесь присутствуют изменения от предыдущей задачи нормализации: перед коммитом проверить `git diff` и состав выбранных файлов.

На VPS, после обновления рабочей копии на нужный коммит:

```bash
cd /root/hyperum
docker compose -f docker-compose.prod.yml build backend
docker compose -f docker-compose.prod.yml up -d --no-deps backend
curl --fail http://127.0.0.1:8000/health/db
```

Обновить также фронтенд: собрать `pwa` через `npm ci` и `npm run build` локально либо на сервере, затем скопировать содержимое `pwa/dist/` в фактический каталог статики Nginx. В [deployment.md](deployment.md) указан пример `/var/www/hyperum`; перед копированием сверить свой действующий конфиг. Сначала обновить backend, затем frontend. После публикации обновить страницу/PWA до новой версии.

На VPS 2026-10-15 подтверждён каталог Nginx `/var/www/hyperum`; Node.js/npm там отсутствуют, поэтому текущую сборку следует выполнять на ноутбуке. После переноса файлов проверить права: Nginx должен иметь возможность проходить в каталоги и читать файлы публичной статики. Каталоги — обычно `755`, файлы — `644`.

### Если после обновления виден прежний интерфейс

При диагностике 2026-10-15 новые HTML, JS и API уже были опубликованы, однако `/var/www/hyperum/assets` принадлежал `root` с правами `700`. Поэтому Nginx возвращал 404 на новый JS, несмотря на наличие файла. Браузер с сохранённой PWA мог продолжать показывать старую версию.

Для этого конкретного случая на VPS достаточно:

```bash
chmod 755 /var/www/hyperum/assets
```

Проверить публичный URL JS из `index.html`: он должен возвращать HTTP 200. Затем закрыть все вкладки сайта и установленное PWA, открыть сайт заново. Если старый интерфейс сохраняется — обновить страницу через Ctrl+Shift+R. Очистку данных сайта оставлять последним шагом: она сбросит локальную сессию.

`git pull` обновляет исходники, пересборка Docker — backend, а `systemctl reload nginx` только перечитывает конфигурацию. Ни одна из этих команд сама по себе не собирает и не публикует PWA. Отсутствие `pwa/dist` в репозитории на VPS не доказывает отсутствие опубликованной сборки: её могли перенести с ноутбука напрямую в каталог Nginx.

## Приёмка после развёртывания

1. Выбрать двух учеников, снять выбор остальных. Проверить поиск по имени и сохранение выбора после очистки поиска.
2. Подобрать персональные наборы, раскрыть карточки и ответ. Заменить одно задание — набор второго ученика должен сохраниться.
3. Включить «Не персонализировать», подобрать общий тест. Проверить текст, формулы и варианты ответа. Заменить позицию: после сохранения и отправки у обоих должны совпадать задания и порядок.
4. До сохранения изменить тему, количество или получателей: старый набор не должен предлагаться к сохранению.
5. Сохранить черновик: настройки и замены блокируются. Отправить и проверить получение только выбранными учениками.

Отправка создаёт реальные назначения — выполнять этот пункт на собственных тестовых аккаунтах. Автоматические проверки не отправляют тесты реальным ученикам. Интеграцию с рабочими PostgreSQL/Neo4j и визуальную приёмку в браузере нужно подтвердить отдельно.
