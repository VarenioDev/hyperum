## 2. Mastery — оценка освоения навыка

### 2.1. Что такое mastery в HyperUm

Mastery — число в диапазоне `[0.0, 1.0]`, отражающее, насколько ученик освоил конкретный навык. Считается **по каждому навыку отдельно**, обновляется после каждого ответа.

**Источник истины:** таблица `student_mastery` в PostgreSQL.  
**Копия для визуализации:** ребро `MASTERY` в Neo4j (best-effort).

### 2.2. Формула

Реализация — в `backend/services/responses_service.py`, функция `update_mastery`.

**Шаг 1. Взвешенные attempts и correct.**

Каждый ответ ученика на задание вносит вклад в mastery **каждого** навыка этого задания. При этом:

- если навык **primary** для задания → вес **1.0**;
- если навык **secondary** → вес **0.7**.

```python
w_attempts = SUM(1.0 if primary else 0.7)
w_correct  = SUM(weight if correct else 0)
```

**Почему так:** primary — то, что задание проверяет по существу. Secondary — сопутствующий навык, задействованный попутно. Давать ему полный вес — искажать картину (ученик решил задачу на вложенные циклы и получил полный балл по «циклу for», хотя это было лишь средство).

**Шаг 2. Байесовское сглаживание.**

```
mastery = (w_correct + PRIOR × WEIGHT) / (w_attempts + WEIGHT)
```

Где:
- `PRIOR = 0.5` — априорная оценка «ученик знает наполовину»;
- `WEIGHT = 3.0` — вес prior'а в виртуальных попытках.

**Смысл:**
- При 1–2 попытках значение тянется к 0.5 — не доверяем единичным данным.
- При 10+ попытках prior почти не влияет — доверяем статистике.

**Примеры:**

| w_correct | w_attempts | mastery |
|-----------|-----------|---------|
| 1 | 1 | (1 + 1.5) / (1 + 3) = **0.625** |
| 0 | 1 | (0 + 1.5) / (1 + 3) = **0.375** |
| 5 | 5 | (5 + 1.5) / (5 + 3) = **0.813** |
| 0 | 10 | (0 + 1.5) / (10 + 3) = **0.115** |
| 10 | 10 | (10 + 1.5) / (10 + 3) = **0.885** |
| 3 | 10 | (3 + 1.5) / (10 + 3) = **0.346** |

### 2.3. Сырые vs взвешенные значения

В таблице `student_mastery` хранятся:

- `mastery` — **взвешенный и сглаженный** (используется в scoring, UI, дашборде);
- `attempts` — **сырое** число попыток (не взвешенное);
- `correct` — **сырое** число правильных.

**Зачем сырые:** для отображения в UI («5 из 8 правильных»). Пользователю неважно, primary это было или secondary.

**Зачем взвешенные:** для расчёта mastery и scoring.

### 2.4. Синхронизация с Neo4j

```python
def sync_mastery_to_neo4j(student_id, skill_id, mastery, attempts, correct):
    try:
        with neo4j_session() as session:
            session.run("MERGE (st:Student {id: $sid})", sid=student_id)
            session.run("""
                MATCH (st:Student {id: $sid})
                MATCH (sk:Skill {id: $skill})
                MERGE (st)-[m:MASTERY]->(sk)
                SET m.value = $val, m.attempts = $att,
                    m.correct = $cor, m.updated_at = datetime()
            """, ...)
    except Exception:
        pass  # best-effort
```

**Ключевое:** `try/except` — если Neo4j недоступен, ответ ученику всё равно возвращается. Mastery в PostgreSQL уже обновлён.

**Техдолг:** в `MERGE (st:Student {id: $sid})` хардкодится `tenant_id = 'school_lyceum'`. Для `demo` — некорректно, но на работу не влияет.

### 2.5. Легаси: `ml/compute_mastery.py`

Старый скрипт, считает mastery **наивно:**

```python
mastery = correct / attempts
```

Полностью **перезаписывает** `student_mastery` для tenant'а.

**Статус:** не используется в проде. Оставлен как batch-утилита для массовых пересчётов (например, после изменения логики сравнения ответов). **Не учитывает:**
- Multi-skill веса.
- Байесовское сглаживание.

**Рекомендация:** либо удалить, либо переписать в соответствии с `responses_service.update_mastery`. Сейчас это источник потенциальной путаницы.

### 2.6. Что в планах

**Фаза 1 (декабрь 2026). BKT.**
Классическая модель Bayesian Knowledge Tracing. 4 параметра на навык
(`p_init`, `p_learn`, `p_slip`, `p_guess`). Обучение на данных пилота.

**Фаза 2 (январь 2027). Graph-BKT.**

навыков. Решает проблему разреженности.

**Фаза 3 (февраль–март 2027). A/B.**
Сравнение эвристики и graph-BKT на живых классах.

**Дальше (после ВКР).** DKT, contextual bandit, GNN на графе, учёт
времени ответа.

См. `research.md`, раздел 6 (план эксперимента) — там же фазы 0–4
с привязкой к календарю.

## 3. Scoring заданий — IRT-подобная функция

### 3.1. Задача

Дан ученик с известным mastery по навыкам и список заданий-кандидатов. Нужно выбрать **N заданий**, максимально полезных для обучения.

**Критерии полезности:**

1. **Зона ближайшего развития** — задание не слишком лёгкое и не слишком сложное.
2. **Бонус слабым** — ученикам с низким mastery нужны задания, дающие прогресс.
3. **Diversity** — не давать одному ученику много заданий на один навык.
4. **Распределение по классу** — задания не должны быть одинаковыми у всех учеников.

### 3.2. Взвешенная mastery для scoring

Перед скорингом effective mastery по заданию считается так:

```python
primary_m = mastery.get(task.primary_skill, 0.5)
secondaries = [mastery.get(s, 0.5) for s in task.all_skills if s != primary]
effective_mastery = (
    0.7 * primary_m + 0.3 * mean(secondaries)
    if secondaries else primary_m
)
```

**Смысл:** если задание требует и `s_for`, и `s_while`, а у ученика `s_for` = 0.8, `s_while` = 0.3, то effective = 0.7×0.8 + 0.3×0.3 = 0.65.

### 3.3. Функция полезности

Реализация — `backend/services/assignments_service.py`, функция `score_task`.

```python
def score_task(mastery, difficulty, usage_count=0):
    # 1. Вероятность правильного ответа (IRT, 1PL — Rasch model)
    delta = mastery - difficulty
    p_correct = 1 / (1 + exp(-4 * delta))

    # 2. Базовая полезность: пик при p_correct ≈ 0.7
    base = exp(-((p_correct - 0.7) ** 2) / 0.08)

    # 3. Бонус слабым ученикам
    if mastery < 0.5:
        base *= 1.4

    # 4. Штраф за повторное использование задания
    diversity_penalty = 1.0 / (1 + 0.5 * usage_count)

    return base * diversity_penalty
```

**Разбор по частям:**

#### 3.3.1. Вероятность правильного ответа

```
p_correct = sigmoid(4 × (mastery − difficulty))
```

**Модель:** 1PL (однопараметрическая) IRT, где параметр «сложности» = `difficulty` из разметки, а «способность» = `mastery` ученика.

**Коэффициент 4** — подобран эмпирически, чтобы кривая была достаточно крутой. При `mastery = difficulty` → p = 0.5.

**Примеры:**

| mastery | difficulty | p_correct |
|---------|-----------|-----------|
| 0.5 | 0.5 | 0.50 |
| 0.7 | 0.5 | 0.69 |
| 0.5 | 0.7 | 0.31 |
| 0.9 | 0.3 | 0.92 |
| 0.1 | 0.7 | 0.08 |

#### 3.3.2. Базовая полезность (гауссиан)

```
base = exp(−(p_correct − 0.7)² / 0.08)
```

**Смысл:** максимальная полезность при `p_correct = 0.7`. Гауссиан с σ ≈ 0.2.

**Почему 0.7, а не 0.5:** задачи с вероятностью 0.5 — на грани возможностей. Психологически комфортнее и продуктивнее чуть выше — 0.7. Это **зона ближайшего развития** по Выготскому.

**Примеры:**

| p_correct | base |
|-----------|------|
| 0.5 | 0.29 |
| 0.6 | 0.61 |
| 0.7 | **1.00** |
| 0.8 | 0.61 |
| 0.9 | 0.14 |
| 0.3 | 0.14 |

#### 3.3.3. Бонус слабым

```
if mastery < 0.5: base *= 1.4
```

**Смысл:** ученику со слабым навыком нужно больше практики. Умножаем полезность на 1.4, чтобы такие задания имели приоритет.

**Почему 1.4, а не 2:** слишком сильный бонус привёл бы к тому, что все слабые получают одно и то же. 1.4 — заметно, но не доминирует.

#### 3.3.4. Diversity-штраф

```
diversity_penalty = 1 / (1 + 0.5 × usage_count)
```

**Смысл:** задание, которое уже раздано другим ученикам в этой генерации, менее полезно. Это **не по причине усталости** (ученики не видят чужие наборы), а для **равномерного покрытия банка**:

- Если задание уникально — все ученики получают разные наборы.
- Если заданий мало — штраф мягкий, задания переиспользуются.

**Примеры:**

| usage_count | penalty |
|-------------|---------|
| 0 | 1.00 |
| 1 | 0.67 |
| 2 | 0.50 |
| 5 | 0.29 |
| 10 | 0.17 |

### 3.4. Отбор с ограничениями

После скоринга — жадный отбор с двумя ограничениями:

```python
selected = []
skill_counts = {}
band_counts = {}

for task in sorted(scored, key=score, reverse=True):
    primary = task.primary_skill
    band = f"{int(task.difficulty * 10) / 10:.1f}"   # 0.1, 0.2, ..., 1.0

    # max_per_skill = 2
    if skill_counts.get(primary, 0) >= 2:
        continue

    # max_per_band = 2
    if band_counts.get(band, 0) >= 2:
        continue

    selected.append(task)
    skill_counts[primary] += 1
    band_counts[band] += 1

    if len(selected) == n:
        break
```

**Смысл ограничений:**

- **`max_per_skill = 2`** — не давать всё на один навык. Если ученик слаб по `s_for`, ему всё равно нужны 2 задания на `s_for` + 3 на смежные.
- **`max_per_band = 2`** — распределение по сложности. Не пихать 5 заданий сложности 0.7, даже если они самые полезные.

**Diversity «band»** — это группировка difficulty по десятой доле: 0.0–0.1, 0.1–0.2, ..., 0.9–1.0. Всего 10 «полос».

### 3.5. Добор

Если после основного прохода выбрано меньше N заданий (мало кандидатов), запускается добор:

**Проход 1:** без `max_per_band`, но с `max_per_skill`.
**Проход 2:** без ограничений вообще.

Это гарантирует, что при нехватке заданий ученик всё равно получит N.

### 3.6. Порядок обработки учеников

Ученики класса перемешиваются (`random.shuffle`). Это важно, потому что `usage_counter` обновляется по мере обхода:

- Первые ученики получают самые «свежие» задания (usage = 0).
- Последние — те, что уже раздавались (usage > 0), но с меньшим приоритетом.

**Почему shuffle:** детерминированный порядок давал бы преимущество одним ученикам (например, по алфавиту). Shuffle выравнивает.

### 3.7. Итог: пример генерации

Класс 10А (3 ученика), тема «Циклы», 5 заданий:

```
Кандидаты: task_001 ... task_050 (все размечены на s_for, s_while, s_nested)

Мастерство:
  Иванов:     s_for=0.3, s_while=0.2, s_nested=0.1
  Петров:     s_for=0.9, s_while=0.85, s_nested=0.7
  Сидорова:   s_for=0.5, s_while=0.4, s_nested=0.3

Результат:
  Иванов:     task_012(dif 0.3), task_008(0.3), task_021(0.4), task_034(0.4), task_047(0.5)
  Петров:     task_005(dif 0.8), task_013(0.8), task_022(0.7), task_041(0.9), task_044(0.7)
  Сидорова:   task_003(dif 0.5), task_010(0.5), task_019(0.6), task_028(0.5), task_039(0.6)
```

**Что видно:**
- Иванов (слабый) — сложности 0.3–0.5.
- Петров (сильный) — сложности 0.7–0.9.
- Сидорова (средняя) — сложности 0.5–0.6.

У каждого — свой набор. Слабые не получают сложных (не фрустрируются), сильные не получают лёгких (не скучают).

## 4. Prerequisite-фильтр

### 4.1. Зачем

Если у ученика провален навык `s_for`, нет смысла давать задания на `s_nested` (вложенные циклы). Ученик не решит и только расстроится.

### 4.2. Алгоритм

Реализация — `assignments_service.get_weak_prerequisites`.

```python
def get_weak_prerequisites(student_id, skill_ids):
    try:
        with neo4j_session() as session:
            result = session.run("""
                MATCH (st:Student {id: $stid})-[m:MASTERY]->(pre:Skill)
                WHERE m.value < 0.5
                MATCH (pre)-[:PREREQUISITE]->(target:Skill)
                WHERE target.id IN $sids
                RETURN DISTINCT target.id AS blocked
            """, stid=student_id, sids=skill_ids)
            return {r["blocked"] for r in result}
    except Exception:
        return set()   # Neo4j недоступен — все задания доступны
```

**Логика:**
1. Найти все навыки, где mastery < 0.5 (провалены).
2. Найти их «цели» — навыки, для которых они являются prerequisite.
3. Если target в списке кандидатов темы — заблокировать.

### 4.3. Порог 0.5

**Почему 0.5:**
- Совпадает с цветовой границей «weak/learning» в UI.
- При mastery = 0.5 вероятность решения зависимого задания ≈ 0.5 — не критично мало.

**Возможное улучшение:** порог 0.4 (мягче) или 0.6 (жёстче) — эмпирически тюнится.

### 4.4. Отсев кандидатов

```python
filtered = [c for c in candidates if c["primary_skill"] not in blocked]
if not filtered:
    filtered = candidates   # fallback: если всё заблокировано — игнорируем фильтр
```

**Fallback важен:** если по теме мало заданий, все они могут быть на заблокированные навыки. Лучше дать хоть что-то, чем ничего.

**Ограничение:** фильтр смотрит только на `primary_skill`. Если задание имеет primary = `s_for` (не заблокирован) и secondary = `s_nested` (заблокирован), оно всё равно пройдёт. Это сознательный компромисс — усложнение проверки на все навыки редко оправдано.

### 4.5. Если Neo4j недоступен

Возвращается пустое множество — все задания доступны. Лучше дать потенциально неподходящее задание, чем не дать ничего.

## 5. Разметка заданий через DeepSeek

### 5.1. Задача

Каждое задание в банке нужно:
1. Привязать к **primary-навыку** (что проверяется в первую очередь).
2. Опционально — к **0–2 secondary-навыкам**.
3. Оценить **сложность** в [0.0, 1.0].
4. Оценить свою **уверенность** в [0.0, 1.0].
5. Дать **reasoning** — текстовое обоснование.

Раньше это делалось вручную или через GigaChat. Сейчас — через **DeepSeek**.

### 5.2. Модель

| Параметр | Значение |
|----------|----------|
| API | `https://api.deepseek.com/chat/completions` |
| Модель | `deepseek-chat` |
| Temperature | 0.2 |
| Response format | `json_object` |
| Timeout | 180 сек |
| Batch size | 10 заданий |
| Max retries | 2 |
| Sleep between batches | 0.5 сек |
| Sleep between retries | 2.0 сек |

**`temperature=0.2`** — низкая, чтобы разметка была стабильной. Не 0.0, чтобы избежать зацикливаний.

### 5.3. Промпт

Полный промпт — в `ml/label_tasks_with_deepseek.py`, константа `SYSTEM_PROMPT_TEMPLATE`.

**Структура промпта:**

1. **Роль:** «опытный методист по информатике».
2. **Схема ответа** (JSON с полями).
3. **Правила multi-skill** (primary + 0–2 secondary, без дублирования).
4. **Рубрика сложности** (0.0–0.2 «очень легко» ... 0.8–1.0 «олимпиадный»).
5. **Эталоны** — 3 примера с эталонными ответами (лёгкий / средний / сложный).
6. **Таксономия** — полный список навыков с ID и названиями (подставляется динамически из YAML).
7. **Правила:** только из списка, difficulty с двумя знаками, task_code точно как во входе, только JSON.

**Приём «эталоны» (few-shot):** показывает модели желаемый уровень детализации и формат. Улучшает качество.

### 5.4. Батчинг

Обрабатывается по 10 заданий за один запрос.

**Плюсы:**
- В ~10 раз меньше HTTP-запросов.
- Модель видит контекст батча → более консистентная разметка.

**Минусы:**
- Один сбой = потеря 10 заданий → нужен fallback.

**Формат входа:**
```
Разметь следующие задания:

─── Задание 1 ───
Код: task_012
Текст: Сколько бит в 4 байтах?

─── Задание 2 ───
Код: task_013
Текст: ...
```

**Формат выхода (ожидаемый):**
```json
{
  "labels": [
    {"task_code": "task_012", "primary_skill": "s_units", "secondary_skills": [], "difficulty": 0.21, "confidence": 0.95, "reasoning": "..."},
    {"task_code": "task_013", ...}
  ]
}
```

### 5.5. Валидация

После получения ответа:

1. **Pydantic-валидация:** `BatchResponse.model_validate(data)`. Проверяет:
   - Наличие поля `labels`.
   - Диапазоны `difficulty` и `confidence` в [0, 1].
   - Типы `secondary_skills` (список строк).

2. **Проверка кодов:** множество `task_code` из ответа должно **точно** совпадать с входом.
   ```python
   returned_codes = {lbl.task_code for lbl in parsed.labels}
   if returned_codes != expected_codes:
       # retry
   ```

3. **Проверка дублирования:** `primary_skill` не должен быть в `secondary_skills` — фильтруется при сохранении.

### 5.6. Retry и fallback

```
┌──────────────────────────────────────┐
│ Батч из 10 заданий                   │
└──────────────┬───────────────────────┘
               │
               ▼
        ┌──────────────┐
        │ Попытка 1    │
        └──────┬───────┘
               │ fail (HTTP / validation / codes)
               ▼
        ┌──────────────┐
        │ sleep 2 сек  │
        │ Попытка 2    │
        └──────┬───────┘
               │ fail
               ▼
        ┌──────────────┐
        │ sleep 2 сек  │
        │ Попытка 3    │
        └──────┬───────┘
               │ fail
               ▼
    ┌──────────────────────────┐
    │ Fallback: по одному      │
    │ (для каждого задания —   │
    │  отдельный запрос)       │
    └──────────────────────────┘
```

**Итого:** 3 попытки батчем + fallback по одному. В худшем случае на 10 заданий — 13 запросов.

### 5.7. Сохранение в БД

```python
def save_label(conn, task_id, label):
```

## 6. Demo: LLM-парсинг описания

### 6.1. Задача

Гость лендинга пишет свободный текст: «Я хорошо знаю системы счисления, умею переводить из 10 в 2. Плохо разбираюсь в кодировании изображений и звука».

Нужно:
1. Определить **тему**, по которой тестировать.
2. Определить **навыки, которые гость знает** (2–5).
3. Определить **навыки, которые не знает** (3–7).

### 6.2. Модель

Та же — DeepSeek `deepseek-chat`. Параметры:

| Параметр | Значение |
|----------|----------|
| Temperature | 0.3 |
| Response format | `json_object` |
| Timeout | 60 сек |

`temperature=0.3` — чуть выше, чем при разметке, потому что описания гостей очень разные, нужна гибкость.

### 6.3. Промпт

```
Ты — методист по информатике. Студент описал свой уровень так:

"{description}"

Доступные навыки (ID | название):
{taxonomy}

Определи:
1. ОДНУ тему (topic) из списка доступных тем — по которой стоит проверить студента.
2. 2-5 навыков (skill_id), которые студент, судя по описанию, ЗНАЕТ.
3. 3-7 навыков (skill_id), которые студент НЕ знает.

Верни JSON строго:
{
  "topic": "...",
  "skills_known": ["s_xxx"],
  "skills_unknown": ["s_yyy"],
  "reasoning": "Краткое пояснение"
}
```

### 6.4. Валидация

```python
if data["topic"] not in topics:
    data["topic"] = random.choice(topics)
```

Если LLM вернула несуществующую тему — берётся случайная. **Причина:** тема определяет, какие задания подавать; неверная тема сломает генерацию.

### 6.5. Применение

1. Создаётся гость (`users` с `tenant_id='demo'`).
2. Для `skills_known` устанавливается mastery = 0.85, attempts = 3, correct = 3.
3. Для `skills_unknown` — mastery = 0.15, attempts = 3, correct = 0.
4. Запускается обычная генерация теста через `select_tasks_for_student`.

**Итог:** гость получает 5 заданий, подобранных по его «синтетическому» профилю.

### 6.6. Ограничения

- **Rate limit:** 5 запусков в час по IP. In-memory `dict`, теряется при рестарте.
- **Cleanup:** гости старше 24 часов удаляются при каждом новом старте.
- **Точность:** LLM может ошибаться в определении known/unknown. Для демо это допустимо.

## 7. Нормализация сложностей

### 7.1. Проблема

LLM склонны **кластеризовать** difficulty в узком диапазоне. Пример: на 100 заданий:

```
0.4–0.5: ████████████████████████ 60
0.5–0.6: ████████████████████     50
0.6–0.7: ████                      8
0.0–0.2:                             0
0.8–1.0:                             0
```

**Почему плохо:** в scoring сложность определяет `p_correct`. Если все задачи имеют difficulty ≈ 0.5, то для сильного ученика (mastery 0.9) все они одинаково бесполезны — ни одна не попадает в ЗБР.

### 7.2. Решение

`ml/normalize_difficulty.py` **растягивает** распределение к равномерному.

**Алгоритм (общий):**
1. Собрать все difficulty для `model='deepseek'`.
2. Построить эмпирическое распределение.
3. Применить монотонное преобразование к равномерному на [0, 1].
4. UPDATE в `task_labels`.

**Сохраняет порядок:** если `task_A` был легче `task_B`, то после нормализации остаётся легче. Меняются только абсолютные значения.

### 7.3. Когда запускать

**После каждой массовой разметки.** Регулярно — раз в неделю или перед пилотной генерацией.

### 7.4. Опции

## 8. Разметка таксономии

### 8.1. Загрузка YAML → Neo4j

`ml/load_taxonomy.py` — читает `taxonomy/informatics_10_11.yaml`, создаёт/обновляет:

```cypher
MERGE (m:Module {name: $module_name})
MERGE (t:Topic {name: $topic_name})
MERGE (s:Skill {id: $skill_id})
SET s.name = $name, s.difficulty = $difficulty
MERGE (m)-[:CONTAINS]->(t)
MERGE (t)-[:CONTAINS]->(s)
```

**Prerequisite:**
```cypher
MATCH (a:Skill {id: $prereq_id})
MATCH (b:Skill {id: $skill_id})
MERGE (a)-[:PREREQUISITE]->(b)
```

**Идемпотентно:** можно запускать многократно.

```sql
ON CONFLICT (id) DO UPDATE
  SET name = EXCLUDED.name,
      module = EXCLUDED.module,

```

### 11.1. BKT (планы)

**Bayesian Knowledge Tracing** — вероятностная модель, оценивающая скрытое «знание» ученика по последовательности ответов.

**4 параметра на навык:**
- `p_init` — вероятность знать навык изначально.
- `p_learn` — вероятность научиться после ответа.
- `p_slip` — вероятность ошибиться, зная.
- `p_guess` — вероятность угадать, не зная.

**Зачем:** учитывает забывание, «переходные» состояния, даёт оценку уверенности.

**Данные для обучения:** ответы пилота (3 класса, 67 учеников).

### 11.2. DKT (планы)

**Deep Knowledge Tracing** — LSTM/трансформер на последовательности ответов.

**Вход:** последовательность `(skill_id, correct)` для ученика.  
**Выход:** вероятность правильного ответа на следующий навык.

**Преимущества:** улавливает сложные зависимости.  
**Недостатки:** требует много данных, плохо интерпретируется.

### 11.3. Bandit (планы)

**Contextual bandit** для рекомендаций. Каждое задание — «рука». Reward — learning gain. Context — текущий mastery, время, история.

**Цель:** переход от эвристического scoring к обучению на реальных данных.

### 11.4. GNN (планы)

**Graph Neural Network** на графе prerequisite. Узел = навык, состояние = mastery. GNN учитывает, что mastery по `s_nested` **зависит** от mastery по `s_for`.

**Преимущества:** использует структуру графа.  
**Статус:** научный интерес, не приоритет.

## 12. Эксперимент в ВКР

Полная рамка — в [`research.md`](research.md). Здесь — краткая сводка.

**Гипотезы:**

- **H1.** Динамически калибрующийся граф знаний даёт более точную оценку mastery, чем статические модели.
- **H2.** Ансамбль ML-моделей подбирает задания точнее, чем единая модель или правила.
- **H3.** Система снижает временные затраты учителя на подготовку персональных заданий.
- **H4.** Гиперперсонализация повышает прирост освоения материала.
- **H5.** Система сохраняет эффективность при переносе школа → платформа без изменения ядра.
- **H6.** Использование клиентского приложения даёт более точную оценку за счёт детальных логов.

**Метрики для H4:**
- Прирост mastery в экспериментальной группе vs контрольной.
- Время до достижения порога mastery = 0.8.
- Вовлечённость (число ответов в неделю).

**Метрики для H2/H1:**
- AUC предсказания правильного ответа.
- RMSE между предсказанным и фактическим mastery.

### Критерии успеха

**Minimum viable result** (защита гарантирована):

- ✅ Работающая система в проде.
- ✅ Данные пилота собраны.
- ✅ H1 и H2 подтверждены **или** опровергнуты с интерпретацией.
- ✅ Реализован graph-BKT (даже отрицательный результат — научный вклад).

**Хороший результат:**

- ✅ H2 подтверждена (BKT > эвристика).
- ✅ H3 подтверждена на редких навыках.
- ✅ Реализован A/B тест.

**Отличный результат:**

- ✅ Всё выше.
- ✅ H4 подтверждена (прирост от гиперперсонализации).
- ✅ H5 подтверждена (переносимость).
- ✅ Публикация или доклад.
