# Нормализация текста заданий

Нормализатор `ml.normalize_task_text_v2` обрабатывает локальный CSV через DeepSeek
и сохраняет Markdown + LaTeX в отдельный каталог. Он не подключается к БД,
не меняет исходный CSV и не запускает разметку навыков.

## Что обнаружено в исходнике

В `tasks/16taskege.csv` 236 заданий. У 201 есть LaTeX-команды, но нет математических
разделителей. Формулы, переменные и условия часто повторены в нескольких
представлениях. В plain-тексте теряются степени и разделители чисел.

Старый `ml.normalize_task_text` захватывает соседний текст и повторно добавляет
`$`; на этом файле все 201 изменённое задание изменяются снова при втором запуске.
Не применять его к этим заданиям в БД. Новый инструмент использует отдельный
промпт, проверяет результаты и хранит оригиналы.

## Запуск из корня проекта

Нужны зависимости `requirements-backend.txt`, установленные зависимости `pwa`
(`npm.cmd ci` внутри `pwa`), Node.js и `DEEPSEEK_API_KEY` в корневом `.env`.
API-вызовы используют баланс DeepSeek. Ключ не попадает в отчёт и предпросмотр;
модель получает только `code` и `text`, без правильного ответа.

```powershell
# Десять разнообразных заданий
.\.venv\Scripts\python.exe -m ml.normalize_task_text_v2 tasks/16taskege.csv --sample --workers 4

# Весь файл (отдельный запуск; выборка повторно берётся из кэша)
.\.venv\Scripts\python.exe -m ml.normalize_task_text_v2 tasks/16taskege.csv --workers 4

# Только выбранные задания
.\.venv\Scripts\python.exe -m ml.normalize_task_text_v2 tasks/16taskege.csv --codes task_831 task_837

# Перепроверить выборку без API-вызовов
.\.venv\Scripts\python.exe -m ml.normalize_task_text_v2 tasks/16taskege.csv --sample --offline

# Отдельная проверка сохранения смысла (также использует DeepSeek и кэш)
.\.venv\Scripts\python.exe -m ml.verify_task_texts data/task_normalization/16taskege/report.json

# Итоговый CSV: прекращает работу при любых нерешённых замечаниях
.\.venv\Scripts\python.exe -m ml.finalize_task_texts data/task_normalization/16taskege/report.json data/task_normalization/16taskege/semantic-review.json
```

Параметры: `--output-dir`, `--limit`, `--model` (по умолчанию `deepseek-chat`),
`--workers` (1–8). Кэш привязан к исходной строке, модели и содержимому промпта;
изменение входа/промпта требует нового API-вызова. Прерывание процесса не мешает
повторному запуску с уже сохранёнными ответами.

## Результаты

По умолчанию результаты находятся в `data/task_normalization/16taskege-sample`
или `data/task_normalization/16taskege`. Каталог `data` исключён из Git.

- `original.csv` — снимок выбранных исходных строк.
- `candidates.csv` — все предложенные тексты, включая требующие проверки.
- `checked.csv` — предложения без предупреждений; для остальных сохранён исходный
  текст. Это не подтверждение математической эквивалентности и не готовый полный
  очищенный банк, если в отчёте остались `needs_review`.
- `report.json` — исходник, кандидат, модель, хэши, расход токенов, предупреждения,
  ошибки рендера, число формул и статус каждой строки.
- `preview.html` — автономный предпросмотр «исходник → результат» с встроенными
  стилями и шрифтами KaTeX. Создаётся из текущего `LatexText.tsx`, без backend.
- `semantic-review.json` — отдельная смысловая проверка исходника и кандидата.
- `verified-report.json`, `verified.csv` — итог после смысловой проверки и,
  при необходимости, ручной сверки. CSV создаётся только если проверены все строки.

В обоих CSV сохраняются все входные колонки, включая `code`, `answer`, `type`;
изменяется только `text`. Снимок выборки содержит только выбранные строки.

## Проверки и ограничения

JSON проверяется схемой Pydantic; код задания должен совпасть. Скрипт проверяет
изменение множества числовых токенов и имён функций, подозрительно короткий текст,
добавление секции ответа/решения, HTML и артефакты символов. Unicode-минус
нормализуется только внутри явных математических разделителей; операция идемпотентна.
Node-скрипт разбирает Markdown и проверяет каждую формулу KaTeX с `strict: error`;
необрамлённые команды и остаточные `$` в обычном тексте помечаются как ошибки.

Проверки не доказывают сохранение знаков, ветвей рекурсии, порядка аргументов,
чётности или всех фраз вопроса. Нужна сверка текста и рендера с исходником.
Числовые предупреждения могут быть ложными: `42 038` превращается в `42038`,
а потерянная степень `1 0 12` восстанавливается как `10^{12}`. Не отключать
проверку целиком: объяснять такие случаи по конкретным заданиям.

На 2026-10-13 обработан снимок реального банка VPS: 976 заданий, 746 текстов
изменены. Все итоговые тексты прошли строгую проверку KaTeX. Отдельный проход
DeepSeek подтвердил 974 кандидата; два случая с повторённым `A A A` в IP-адресе
сверены вручную. Всего 41 запись имеет ручную сверку (числа, степени, блоки кода,
переменная X, исходные неоднозначности и два исправления оформления).
Предпросмотр проверен в headless Edge на desktop. Бэкап PostgreSQL, снимок
текстов и старая статика сохранены на VPS в `data/normalization-20261013`.
Тексты применены в production; разметка восстановлена для всех 201 задания без
меток. После применения в БД 976 заданий и 1906 меток, 0 заданий без primary-метки
DeepSeek. Публичная страница и assets совпали со сборкой, авторизация без токена
вернула 401; демо вернуло 5 заданий с точными текстами и ID из итогового CSV.
Все 9 тестов и production-сборка frontend прошли.

Ручные согласования передаются `--approvals manual-approvals.json` в финализатор.
Формат: объект с ключами-кодами заданий; каждое значение содержит
`original_sha256`, `candidate_sha256`, `note` и при необходимости `normalized_text`.
Хэши считаются от UTF-8 текста, поэтому согласование не переносится на другой
исходник/кандидат. Ручная сверка не может обойти ошибку API или ошибку KaTeX.

## Обновление VPS после проверки

Применять только проверенные тексты, обновляя существующие задания по `code`
и сохраняя их `id`, ответы и связи с назначениями. Перед обновлением сохранить
снимок текстов; отдельно подтвердить, что в БД всё ещё исходная версия.
Нормализатор не выполняет этот шаг автоматически. Затем размечать навыки через
DeepSeek отдельным запуском. Обычный повторный импорт исходного CSV перезапишет
нормализацию. `scripts.import_tasks` по умолчанию запускает GigaChat-разметку,
поэтому для импорта без неё требуется `--import-only`.

Для production есть отдельная утилита `scripts.task_text_release`, которая
экспортирует `id, code, text, answer, type` и применяет изменения только `text`
по сохранённым `id`. Она блокирует выбранные строки, сверяет БД с исходным
снимком и обновляет все тексты одной транзакцией. Ответы, ID, метки и назначения
не меняются. Резервная копия текстов записывается до коммита.

```bash
# В backend-контейнере; пути — внутри контейнера
python -m scripts.task_text_release export /tmp/tasks-before.csv
python -m scripts.task_text_release apply /tmp/tasks-before.csv /tmp/verified.csv /tmp/texts-before.json
python -m ml.label_tasks_with_deepseek
python -m scripts.check_task_text_release /tmp/verified.csv

# Откат только текстов, без отката новых ответов учеников
python -m scripts.task_text_release apply /tmp/verified.csv /tmp/tasks-before.csv /tmp/texts-before-rollback.json
```

Node и frontend-зависимости нужны только для локальной нормализации/рендера.
В production-контейнер передаётся уже проверенный CSV. Сборка frontend публикуется
через `scripts/deploy_task_text_frontend.sh`: сначала assets, затем атомарно index
и service worker; предыдущие assets сохраняются для открытых клиентов.
